## Failure mode 1 — ASR on the customer's name blocks authentication (4/5 tasks)

All five tasks are the same customer, `yusuf_rossi_9620`. Four of five opened with the
identical mangling:

```
find_user_id_by_name_zip {"first_name": "Youssef", "last_name": "Rossi", "zip": "19122"}
  → Error: User not found
```

`Yusuf → Youssef` is deterministic — it reproduced on every task, across separate LiveKit
sessions. Note the zip is **correct** here (`19122`); the name alone is enough to miss. That
refines the earlier read: name mangling is the primary failure, and the zip corruption seen
previously (`199122`, `191222`) was a secondary artifact of re-spelling under pressure. Task 2
did mangle both (`19132`).

**What separates the recoveries from the give-ups is the agent's retry policy, not the ASR.**

- **Task 3 re-asked and got it right on the second attempt** — `Youssef` failed, it asked
  again, heard `Yusuf`, authenticated, and went on to make 10 tool calls. So the ASR ceiling
  is not hard; a second pass at the name clears it.
- **Task 0 routed around auth entirely** — took the order ID (`#W2378156`) directly and
  completed the exchange. This is the one pass.
- **Tasks 1, 2, and 4 called `transfer_to_human_agents` after a single failed lookup.** Each
  transfer summary faithfully records the wrong name (`"Customer Youssef Rossi with zip code
  19122…"`), so the handoff carries the ASR error forward to the human.

Three of five tasks were lost to giving up after one attempt at a lookup that task 3 shows is
recoverable on the second. That is a cheaper fix than better ASR: retry name-and-zip auth at
least once, or fall back to email (validatable against a known set) before transferring.

## Failure mode 2 — availability filtering, and it is not a voice problem

Tasks 2, 3, and 4 all missed the same assertion: *"Agent should tell the user that there are
10 t-shirt options available."*

```
task 3 — "The agent told the user that there are 12 t-shirt options available, but the
          product data lists 12 variants, of which 2 are unavailable
          (5047954489 and 3542102174). Therefore, there are 10 available options."
task 4 — same: counted all 12 variants, did not filter `available: false`.
task 2 — never got there; transferred to a human before addressing the inquiry.
```

**Task 3 is the important one: it authenticated cleanly, made 10 correct tool calls, and
still scored 0.0.** Nothing about the voice channel caused this — the agent had the product
JSON in hand and did not filter on the `available` flag. This would fail identically in text,
and it is invisible if you attribute every voice-run failure to ASR.

## Reading the two together

The 5-task sample is small and the error bars are wide, but the failure attribution is clean
because the trajectories are unambiguous:

| cause | tasks | voice-specific? |
|---|---|---|
| gave up after one ASR-mangled auth lookup | 1, 2, 4 | partly — ASR triggers it, retry policy decides it |
| counted unavailable product variants | 3, 4 (and 2, blocked earlier) | **no** |
| completed | 0 | — |

The prior conclusion — that voice degradation is ASR on spelled alphanumerics — holds and now
has a name-based instance to go with the order-ID one. But it is not the whole story: task 3
is a clean-authentication failure, so at least part of the text→voice gap reported earlier is
a product-reasoning gap that voice merely happened to be measuring.

## Caveats

- N=5, single trial each. Directional, not a confidence interval.
- All five tasks share one customer, so the `Yusuf → Youssef` mangling is one ASR sample
  repeated, not four independent ones. A broader run over distinct names is needed before
  claiming a name-ASR rate.
- Every task ended in `user_stop` with 0 judged agent errors — the agent is behaving
  sensibly throughout; these are outcome failures, not conduct failures.
